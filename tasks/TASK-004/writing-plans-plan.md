# TASK-004 — Заглушки фронтенда без реализации в бэкенде: план

Основание — сверка фронтенда с бэкендом от 2026-10-23. Все HTTP-вызовы фронтенда (`frontend/src/**/*-api.ts`, `use-*.ts`) совпадают с контроллерами в `apps/*`: висящих запросов нет. Заглушки — это **статический контент и экраны, за которыми нет данных или эндпоинтов**.
Правила: `AGENTS.md`, `.claude/DOD.md`; тест сначала; коммит `feat|fix(<scope>): …`; без push; `.env` не читать. После каждой задачи — пауза и отчёт владельцу (см. TASK-003). Реализацию задач не начинать без команды.

Отсутствие графиков в аналитике (`recharts` не установлен) и тесты `test.fixme` в `frontend/e2e` — недоделки фронтенда, но не «фронт без бэка»; в этот план не входят.

- **S1.** Конфигурация клиники в переменных окружения/сидере (`Organization` в HAPI) либо оставить константы, но вынести в один файл конфигурации.
- **S2–S4.** Реализовать модель (`Organization`, `Coverage`, поле в записи) либо убрать блоки «Нам доверяют», «Компаниям», «По страховке» с лендинга; промежуточный вариант — оставить тексты без обещаний (без списков, без «договор/полис»).

Вопросы владельцу — в отчёт. Без кода.

## T2 — Сведения о клинике из бэкенда (S1)

**Шаги (детализировать после T1).**
1. Тест сначала (сервис — по выбору T1; кандидат — catalog-service): публичный `GET /api/v1/clinic` (без авторизации) → `{ name, unp, license{number,date}, phone, email, address, hours }`; в спеках — раздел API, не дублируя уже описанное.
2. Данные: сидер `seed:demo` и `.env.example` (имена переменных, значения не печатать).
3. Фронтенд: `catalog-server.ts` читает сведения на сервере; `home-content.ts` теряет `CLINIC_*`; `home.demoNote` показывать только при демо-флаге ответа (`demo: true`).
4. Проверки: `npx nx run-many -t test lint build -p <service> --parallel=1`; `cd frontend && npx tsc --noEmit && npx next lint && npx jest`; `npm run smoke:stack`.
5. Коммит: `feat(catalog): serve the clinic's public details instead of hard-coded text`.

## T3 — Направления из справочника (S5)

**Шаги.**
1. Тест сначала (`home-view.spec.tsx`, `doctor-directory.spec.ts`): карточка направления ведёт на `/doctors?specialty=<code>`; направление без врачей не показывается (или помечается).
2. `DIRECTIONS` получает поле `specialtyCode` (SNOMED, как в `Doctor.specialtyCode`); соответствие сверить с демо-данными врачей и справочником `catalog-service`; направление «Диагностика» — привязать к услугам (`?serviceId=`), а не к специальности.
3. Проверки как в T2 (только фронтенд); `browser-verify` лендинга.
4. Коммит: `fix(web): link landing directions to the doctor catalog filters`.

## T4 — Профиль: правка контактов и телефон (S6)

**Шаги (детализировать после T1).**
1. Бэкенд (patient-service): `PATCH /me/patient` — только контакты (`telecom`: телефон, e-mail); валидация формата (Беларусь: `+375…`), 409 при гонке (`If-Match`, ADR-012), `AuditEvent` на изменение; ADMIN/DOCTOR не могут править чужие через этот путь.
2. auth-service: e-mail учётной записи — отдельное решение T1 (смена логина); по умолчанию не трогаем.
3. Фронтенд: форма на экране «Профиль» (`components/patient/profile/`), поле телефона в `register-form.tsx` + `register-schema.ts`, текст `readOnly` в `messages/{ru,en}.json` заменить; убрать `phoneMissing`-предупреждение или оставить как подсказку.
4. Тесты, спека (`api-designer-spec.md` — новая строка в разделе 3), smoke, живая проверка.
5. Коммит: `feat(patient): let a patient edit their own contacts`.

## T5 — Корпоративные клиенты, ДМС, заявка (S2–S4)

Планируется после T1; если владелец выберет «убрать», задача сводится к удалению блоков и текстов (`home-audiences.tsx`, `home-content.ts`, ключи `home.aud*`/`home.partners*`, тест `home-view.spec.tsx`) и закрывается одним коммитом `fix(web): remove landing blocks the service cannot back`.
Если «реализовать» — отдельный дизайн (`brainstorming-*`): `Organization`, `Coverage`, приём заявки (`POST /api/v1/inquiries` с защитой от спама), способ оплаты в записи.
