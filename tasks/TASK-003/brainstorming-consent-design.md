# Дизайн: учёт согласия пациента на электронную медкарту (FHIR `Consent`)

Дата: 2026-10-22 · Ветка: `fix/pdn-admin-access` · Задача: TASK-003 / T3 (решение D-4) · Статус: **Draft; правовые ответы получены (§8), ждёт подтверждения юриста клиники**. Только дизайн, кода нет.

## 1. Контекст

Нормы — по ссылке, не дублируются: `tasks/TASK-003/architect-pdn-access-decision.md`, §3, **N5** (основание — ст. 44 ч. 13 Закона «О здравоохранении» и постановление Минздрава № 74 (2021): письменное согласие на внесение сведений в электронную медкарту или ИС; ст. 18 ч. 2 лишь определяет, кто дает согласие за пациента; см. `tasks/TASK-003/architect-consent-legal-answers.md`) и **N6** (постановление № 75 (2021): структура электронной медкарты и личного кабинета). Решение D-4 требует зафиксировать согласие и без него запретить внесение данных. Сейчас всё хранится в электронном виде, согласия система не знает.

Дизайн опирается на текущий код (проверено):
- Пациент появляется двумя путями, оба идут через `apps/auth-service/src/modules/users/account-factory.service.ts`: саморегистрация `POST /auth/register` (2.2.6) и создание ADMIN'ом `POST /admin/users` (2.2.1). Фабрика создаёт `auth.user`, FHIR `Patient`, `ExternalLink` и событие `patient.registered.v1`; при сбое откатывает созданное.
- Запись 6.1: `AppointmentsService.book` создаёт `Appointment` и `AuditEvent` одной транзакцией, пациент берётся из JWT.
- Приём: 7.1 открывает `Encounter`, 7.3 `EncountersService.complete` пишет диагнозы, `ServiceRequest`, `MedicationRequest` одной транзакцией. Именно 7.3 вносит клинические данные в карту.
- Каждый BFF-сервис имеет свой FHIR-клиент (`FHIR_CLIENT`) и читает HAPI напрямую; общий код лежит в `libs/fhir` (например, `PatientReadAudit`).

## 2. Модель FHIR R4 `Consent`

Структура и параметры поиска сверены с HL7 R4 (`consent.html`). Ограничения R4: нужен `policy` **или** `policyRule`; при `scope=patient-privacy` обязателен `patient`.

### 2.1 Пример (согласие подписано на бумаге при регистрации, внесено администратором)

```json
{
  "resourceType": "Consent",
  "id": "demo-consent-<patientId>",
  "identifier": [{ "system": "urn:medcenter:consent-form-number", "value": "ЭМК-2026-000123" }],
  "status": "active",
  "scope": {
    "coding": [{ "system": "http://terminology.hl7.org/CodeSystem/consentscope", "code": "patient-privacy" }]
  },
  "category": [
    { "coding": [{ "system": "http://loinc.org", "code": "59284-0", "display": "Consent Document" }] },
    { "coding": [{ "system": "urn:medcenter:consent-category", "code": "emr-processing" }] }
  ],
  "patient": { "reference": "Patient/1442" },
  "dateTime": "2026-10-22T09:30:00+03:00",
  "performer": [{ "reference": "Patient/1442" }],
  "organization": [{ "reference": "Organization/<clinicOrgId>" }],
  "sourceAttachment": {
    "contentType": "application/pdf",
    "title": "Согласие на внесение сведений в электронную медкарту",
    "url": "Binary/<scanId>",
    "hash": "<sha1-base64>",
    "creation": "2026-10-22T09:30:00+03:00"
  },
  "policyRule": {
    "text": "Закон «О здравоохранении», ст. 44 ч. 13; постановление Минздрава № 74 (2021)"
  },
  "provision": { "type": "permit", "period": { "start": "2026-10-22" } }
}
```

Кодовая система `consent-category` и system для `identifier` — наши собственные; `legal-basis` не вводим, норма идёт текстом в `policyRule.text`. Готовых белорусских кодов не найдено; используем `urn:medcenter:...` (ответ 9 в `tasks/TASK-003/architect-consent-legal-answers.md`).

### 2.2 Решения по элементам

| Элемент | Решение | Почему |
| --- | --- | --- |
| `status` | `active` — действует; `inactive` — отозвано пациентом или истекло. `rejected` — **рекомендуем писать** при письменном отказе пациента (чтобы не просить повторно и знать, что карта ведётся на бумаге); `entered-in-error` — только для ошибки оператора (не отзыв). `draft`/`proposed` не используем | В R4 `inactive` — «больше не действует», `rejected` — «отказано/не дано», `entered-in-error` — ошибочная запись. Отзыв не должен выглядеть как ошибка |
| `scope` | **`patient-privacy`** (рекомендуем). Альтернатива `treatment` (согласие на лечение) — смысл другой, у нас это не предмет ст. 44 ч. 1–7 | Согласие касается обработки и раскрытия сведений о пациенте, это «privacy». У `patient-privacy` в R4 обязателен `patient` — у нас он всегда есть |
| `category` | LOINC `59284-0` (общий «Consent Document») + наш `emr-processing`. Для поиска хватит нашего | Категория — индексная метка, расширяема |
| `patient` / `performer` | `patient` — всегда. `performer` — `Patient` или `RelatedPerson` (представитель: все младше 18 лет, опекун, супруг или родственник; ответ 7). Подписавший медработник — отдельное поле (extension или `note`), ответ 2 | N5: «пациента (законного представителя)». Доверенные лица уже есть как `RelatedPerson` (3.3) |
| `dateTime` | Момент **подписания** (с бумаги), а не момент ввода. Момент ввода — в `meta.lastUpdated` и `AuditEvent` | Для юридической ценности важна дата подписи |
| `organization` | Организация клиники (в сиде есть `Organization`) | Держатель согласия — оператор |
| `policyRule` | Только `text` со ссылкой на норму (см. 2.1), без кода. `policy.uri` не используем | R4 требует одно из двух; код нормы быстро устаревает (ответ 9) |
| `sourceAttachment` | Скан бумажной формы. `url` — `Binary/{id}` в HAPI, `hash` обязателен. Для самостоятельного электронного согласия — **нет вложения**, вместо него `identifier` (версия текста согласия) | Файлового хранилища в проекте нет; `Binary` в HAPI — минимальный вариант (вопрос владельцу 6) |
| `provision` | `type=permit`, `period.start` = дата подписи, `period.end` — пусто (бессрочно) или дата отзыва/истечения. Вложенные ограничения (`actor`, `class`, `data`) не используем: правило одно — «ведение электронной карты» | Просто и проверяемо. Тонкие запреты («скрыть от врача X») за пределами N5 |
| Отзыв | Обновить тот же `Consent`: `status=inactive`, `provision.period.end=<дата отзыва>`. История версий HAPI сохраняет прежнее состояние. Новое согласие после отзыва — **новый** `Consent` | Один действующий `Consent` на пациента и область; журнал не теряется |
| `verification` | Не используем (проверка подписи = регистратор, фиксируется `AuditEvent`) | Избыточно |

### 2.3 Поиск (используют сервисы)

- «Есть ли действующее согласие»: `GET Consent?patient=Patient/{id}&scope=patient-privacy&category=urn:medcenter:consent-category|emr-processing&status=active&_sort=-date&_count=1`. Срок (`provision.period.end` в прошлом) проверяется в коде: сервис не доверяет `status` одному.
- История согласий пациента: `Consent?patient=Patient/{id}&_sort=-date`.
- Согласие по скану/номеру формы: `Consent?identifier=` и `source-reference` (для `sourceReference` на `DocumentReference`, если когда-либо перейдём на него).

## 3. Где и когда фиксируется согласие

| Вариант | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| **A. При саморегистрации** | Обязательный флажок на форме `POST /auth/register`: текст согласия + версия. `Consent` создаётся в той же фабрике, что и `Patient`; `performer=Patient`, `sourceAttachment` нет | Согласие есть до первого внесения данных; нет «пустых» пациентов; без ручного труда | Флажок не является письменным согласием (ответ 1): годится только как согласие по ст. 5 № 99-З на учётную запись; не покрывает пациентов, заведённых ADMIN'ом, и унаследованные записи |
| **B. На регистратуре ADMIN'ом (бумага + скан)** | Пациент подписывает бумажную форму, ADMIN вносит `POST /patients/{id}/consent` с номером формы и сканом | Прямое соответствие «письменному согласию»; ADMIN согласно N7 работает с идентификацией; не нужен врач | Узкое место на регистратуре; нужен `Binary`-загрузчик; самозарегистрированный пациент до визита без согласия |
| **C. Врачом перед первым приёмом** | Врач при открытии приёма (7.1) подтверждает и вносит согласие | Точка, где данные реально идут в карту | Врач тратит время приёма; нет бумажного канала с ADMIN; смешивает роли |

**Решение (ответы 1, 2 в `tasks/TASK-003/architect-consent-legal-answers.md`):** B для **всех** пациентов (бумага со сканом, подписи пациента или представителя и медработника). Вариант A — только согласие на учётную запись (отдельная категория, не `Consent emr-processing`). Вносят ADMIN **и** DOCTOR (поле «медработник, подписавший форму»); вариант C равноправный.

**Отзыв.** Пациент в личном кабинете: `POST /me/consent/{id}/revoke` — сразу блокирует новые записи, затем подтверждается письменным заявлением (ответ 5); заявление в клинике — ADMIN или DOCTOR: `POST /patients/{id}/consent/{cid}/revoke` с номером заявления. Эффект: новые данные не вносятся (блокировка из §4), уже внесённые не удаляются автоматически (обязанность хранить мед. документы; срок хранения не проверен, ответ 5).

## 4. Что блокируется без активного согласия

Варианты ниже; выбранное решение — в конце раздела.

| Вариант | Влияние на пользователей | Юридическое соответствие |
| --- | --- | --- |
| **1. Блок 7.3 (и 7.1)**: врач не может открыть/завершить приём, 409 `CONSENT_REQUIRED` | Пациент записан и пришёл, а врач упирается в отказ; нужна подсказка «оформите согласие у регистратора». Данные в карту не попадают | Прямо исполняет N5: клинические данные вносятся только после согласия. `Appointment` в системе уже есть |
| **2. Блок 6.1**: запись без согласия невозможна | Пациент сразу видит причину, при саморегистрации согласие даётся ещё до записи; ADMIN-созданные пациенты не могут записаться из кабинета | Самый строгий, `Appointment` содержит ПДн (кто, к кому, причина). Ломает запись «по телефону» через регистратуру |
| **3. Только предупреждение** (баннер у врача/ADMIN, запись в аудит) | Нет сбоев в потоке | Не исполняет «только с согласия»: годится как переходный этап |
| **4. Оставить на бумаге** (согласие учитывается вне системы) | Без изменений | Нарушает D-4: система не может доказать наличие согласия; N5 требует согласие до внесения в ИС |

**Решение (ответы 3, 4, 8):** вариант 1 (блок 7.1 и 7.3, 409 `CONSENT_REQUIRED`) + предупреждение при 6.1; свободный текст «причина обращения» без согласия не принимается. Режим `CONSENT_ENFORCEMENT=warn|block` (после запуска `block`). Экстренная ветка: `emergencyReason` в 7.1/7.3 при неспособности пациента дать согласие, отдельная запись в аудит, согласие оформляется после. Письменный отказ: `Consent.status=rejected`, помощь на бумаге вне системы. Блок 6.1 (вариант 2) — на усмотрение юриста.

## 5. Владелец, эндпоинты, доступ, аудит

**Владелец ресурса:** `patient-service` (он владеет `Patient`/`RelatedPerson` по матрице владения ADR; `Consent` — «административное» продолжение пациента), модуль `apps/patient-service/src/modules/consents/`. `auth-service` при саморегистрации `Consent emr-processing` **не** создаёт: флажок — только согласие на учётную запись по ст. 5 № 99-З (поле в `auth.user` с версией текста; ответ 1). `appointment-service`/`encounter-service` **не вызывают** patient-service: читают `Consent` из HAPI своим `FHIR_CLIENT` через общий помощник в `libs/fhir` (`assertActiveConsent`), как сделано для аудита.

**Эндпоинты (набросок, §3 спеки продолжает 3.1–3.3):**

| № | Метод и путь | Назначение | Доступ |
| --- | --- | --- | --- |
| 3.4 | `GET /api/v1/me/consent` | своё действующее согласие и история | `patient/*.read` |
| 3.5 | — | не вводим: электронное согласие на ЭМК без ЭЦП не даётся (ответ 1) | — |
| 3.6 | `POST /api/v1/me/consent/revoke` | отозвать своё (сразу блокирует новые записи; письменное заявление — потом, ответ 5) | `patient/*.write` |
| 3.7 | `GET /api/v1/patients/{id}/consent` | статус и история | `user/*.read` (DOCTOR/ADMIN) |
| 3.8 | `POST /api/v1/patients/{id}/consent` | внести бумажное согласие или письменный отказ: номер формы, дата подписи, **скан обязателен**, подписавший медработник, `performer` (`Patient`/`RelatedPerson`) и документ полномочий представителя | `ADMIN`, `DOCTOR` |
| 3.9 | `POST /api/v1/patients/{id}/consent/revoke` | зафиксировать письменный отзыв (номер заявления) | `ADMIN`, `DOCTOR` |

Скан: `POST /api/v1/patients/{id}/consent/scan` (→ `Binary`, PDF/JPEG/PNG до 10 МБ, ответ 6) — отдельным эндпоинтом. Новые ошибки: 409 `CONSENT_REQUIRED` (7.1, 7.3), 409 `CONSENT_ALREADY_ACTIVE` (3.8). Маршруты `me/consent` нужно добавить в `infra/traefik/dynamic.yml` (там `me/patient` описан отдельным правилом).

**Матрица ПДн (§0 спеки), добавляется строка:**

| Категория | PATIENT (свои) | DOCTOR (со связью) | ADMIN |
| --- | --- | --- | --- |
| Статус и история согласия | да, может отозвать | чтение и внесение бумажного | чтение и внесение бумажного (медицинских данных не видит, ADR-018) |

Состав согласия — административные данные; ADMIN допустим по N7 (регистратор). Компартмент: DOCTOR читает и вносит согласие только пациента со связью (ADR-013).

**AuditEvent (ADR-014, T2).** Создание, отзыв и внесение скана пишутся `AuditEvent` в той же транзакции (`auditWrite`, `action=C`/`U`, `entity=Consent/{id}`, `agent` — пользователь, `patient` — пациент). Чтение 3.7 DOCTOR/ADMIN'ом журналируется как чтение через `PatientReadAudit` (`read`/`denied`); чтение пациентом себя — нет (как в T2). Чтение скана журналируется **всегда**, любым пользователем. Экстренный обход (`emergencyReason` в 7.1/7.3) — отдельный `AuditEvent` с причиной. Проверки внутри 7.1/7.3 не журналируются, но 409 `CONSENT_REQUIRED` — в лог запроса. Отказ по согласию — `outcome=4`, чтобы виден был в аудите.

## 8. Решения и открытые вопросы

Решения с обоснованием — `tasks/TASK-003/architect-consent-legal-answers.md` (ответы 1–9), здесь только итог:

1. Флажок при саморегистрации — не письменное согласие на ЭМК; только согласие на учётную запись.
2. Бумажное согласие вносят ADMIN и DOCTOR; подписавший медработник обязателен.
3. Переходного периода нет: до запуска `warn`, после — `block`; задним числом согласий не создаём.
4. Блок 7.1 и 7.3 (409 `CONSENT_REQUIRED`); 6.1 — предупреждение без свободного текста причины; письменный отказ — `rejected`, помощь на бумаге.
5. После отзыва ничего не удаляем, новые данные блокируем; ограничение чтения — после T4.
6. Скан обязателен (`Binary`, хэш, номер и дата формы), чтение скана журналируется.
7. Представители — в этой версии (`RelatedPerson`), для всех младше 18 лет.
8. Узкая экстренная ветка с `emergencyReason` и отдельным аудитом; «break the glass» — вне T4.
9. Свой код только `consent-category`, норма — текстом в `policyRule.text`, домен `urn:medcenter:...`.
