# Решение: доступ к персональным данным пациента по ролям (законодательство РБ)

Дата: 2026-10-22 · Ветка: `fix/known-gaps` · Статус: **Proposed** (ждёт утверждения владельцем; после утверждения переносится в `specs/architect-architecture.md` как ADR-018)

## 1. Вопрос

Какие персональные данные (ПДн) пациента может видеть каждая роль системы (PATIENT, DOCTOR, ADMIN)? Поводом стала запись `Patient compartment violation` в логе patient-service: врач `doctor.ivanova` запросил карточку пациента 1442 (Лебедева), с которым у него были только отменённые записи. Сервис отказал (403).

## 2. Что говорит HL7 FHIR R4

Правил не задаёт. В разделе *Security* сказано, что FHIR не является протоколом безопасности и не определяет функции безопасности. Решение о доступе принимает внешняя система (RBAC/ABAC) с учётом роли, связи пользователя с пациентом, согласия (`Consent`), цели доступа (purpose of use) и меток конфиденциальности. Раздел *CompartmentDefinition* описывает компартменты Patient и Practitioner лишь как «основу для применения контроля доступа». Значит, правило берётся из законодательства Республики Беларусь (FHIR International R4 остаётся базой для формата данных, см. `AGENTS.md`).

## 3. Нормы Республики Беларусь

Источник — официальные сайты (pravo.by, etalonline.by, cpd.by, minzdrav.gov.by), поиск от 2026-10-22. Полный текст рекомендаций НЦЗПД по здравоохранению прочитать не удалось: сервер cpd.by ответил 503. Номера частей статей сверить с действующей редакцией на pravo.by до финальной защиты.

| № | Норма | Содержание (пересказ) |
|---|---|---|
| N1 | Закон «О здравоохранении» № 2435-XII, **ст. 46** | Факт обращения, состояние здоровья, диагноз и иные сведения, полученные при оказании помощи, составляют врачебную тайну. Без согласия пациента их передают только в случаях, перечисленных в законе (запросы уполномоченных органов, угроза жизни и здоровью других людей, вред от противоправных действий и др.). Обязанность хранить тайну распространяется на всех, кому сведения стали известны. |
| N2 | Закон «О защите персональных данных» № 99-З, **ст. 8** | Данные о здоровье — специальные ПДн. Без согласия их обработка по общему правилу запрещена. Исключение — организация оказания медицинской помощи работником, обязанным хранить врачебную тайну, а также экстренная помощь. Обработка специальных ПДн допустима только при комплексе мер против рисков для прав субъекта. |
| N3 | Закон № 99-З, **ст. 4** | Обработка соразмерна заявленным целям, ограничена конкретными законными целями; избыточная обработка не допускается (комментарий НЦЗПД к ст. 4). |
| N4 | Закон № 99-З, **ст. 17, п. 3** | Оператор обязан установить порядок доступа к ПДн, в том числе в информационных системах. По комментарию НЦЗПД порядок строится на «минимально необходимом уровне доступа» для должностных обязанностей; для цифровых данных — через настройки ПО. |
| N5 | Закон «О здравоохранении», **ст. 44 ч. 13**; постановление Минздрава **№ 74** (2021); ст. 18 ч. 2 определяет, кто дает согласие за пациента (подробнее: `tasks/TASK-003/architect-consent-legal-answers.md`) | Вносить сведения о пациенте в электронную медицинскую карту или информационную систему можно только с письменного согласия пациента (законного представителя). При отказе — бумажный учёт. НЦЗПД разъясняет так же: на бумаге согласие не нужно, при автоматизированной обработке нужно. |
| N6 | Постановление Минздрава **№ 75** от 07.06.2021 | Структура и порядок формирования электронной медкарты и личного кабинета пациента. Доступ к ним предоставляется в порядке ст. 46 (N1). |
| N7 | Рекомендации **НЦЗПД** по обработке ПДн в здравоохранении | Доступ к данным пациента нужен не только врачам, но и работникам, которые обеспечивают помощь (регистратор, бухгалтер, юрисконсульт), но только в объёме их задач. Требуются разграничение доступа и перечень работников с доступом. |

## 4. Решения

| № | Решение | Обоснование |
|---|---|---|
| D-1 | **Оставить** правило для врача: DOCTOR видит карточку, историю, назначения и доверенных лиц только того пациента, с которым у него есть общая `Appointment` в статусе `booked`/`arrived`/`checked-in`/`fulfilled` или `Encounter` (`patient-access.service.ts`). Отказ в логе признан корректным. | N2 (обработка без согласия — для оказания помощи этому пациенту), N3 (без избыточности), N4 (минимально необходимый доступ). Отменённая запись или неявка помощи не означают. |
| D-2 | **Ограничить** ADMIN: администратор видит идентификационные и контактные данные пациента (3.2, 3.3), но **не** медицинские: история обращений 7.4 и назначения 7.5 для ADMIN закрываются (403 `COMPARTMENT_VIOLATION`). Агрегированная аналитика (9.x) без диагнозов конкретного лица остаётся. | N1 (врачебная тайна — сведения, полученные при оказании помощи; администратор помощь не оказывает), N3, N4, N7 (доступ в объёме задач: учётки, расписания, кабинеты). |
| D-3 | **Журналировать чтение**: каждое успешное чтение карточки, истории и назначений чужого пациента (3.2, 3.3, 7.4, 7.5) пишет `AuditEvent` (`action=R`, `subtype=read`), без тел ответов. Отказ (403) тоже пишется. Сейчас аудит есть только для записей (ADR-014). | N2 («комплекс мер» для специальных ПДн), N4 (порядок доступа нужно контролировать), FHIR Security §Audit (AuditEvent для событий доступа). |
| D-4 | **Спроектировать** учёт согласия пациента на электронную медкарту (FHIR `Consent`): фиксировать согласие при регистрации или первом визите, без него запрещать внесение данных в электронную карту. Реализация — после отдельного дизайна. | N5, N6. Сейчас система хранит всё в электронном виде и согласия не фиксирует. |
| D-5 | **Документировать** матрицу «роль → категории данных → эндпоинты» в `specs/api-designer-spec.md` (§0 «матрица доступа»), а решение — как ADR-018 в `specs/architect-architecture.md`. | N4, N7 (перечень и порядок доступа должны быть утверждены документом оператора). |

## 5. Матрица доступа (целевая, после D-2)

| Категория данных | PATIENT (свои) | DOCTOR (пациенты с общей записью или приёмом, D-1) | ADMIN |
|---|---|---|---|
| Идентификация и контакты (3.2) | да | да | да |
| Доверенные лица (3.3) | да | да | да |
| История обращений, диагнозы (7.4 / 7.6) | да | да | **нет** (D-2) |
| Назначения (7.5 / 7.7) | да | да | **нет** (D-2) |
| Аналитика 9.1–9.3 (агрегаты) | — | — | да |
| Журнал аудита 9.4 | — | — | да |

## 6. Не решено, вопросы владельцу

- Нужен ли экстренный доступ («break the glass», N2: экстренная помощь) для врача без общей записи — с обязательной причиной и записью в аудит. По умолчанию — нет.
- Имеет ли ADMIN-руководитель (главврач) право читать медицинские данные для экспертизы качества помощи. По умолчанию — нет; если да, это отдельная роль с аудитом.
- Срок, после которого связь «врач — пациент» перестаёт давать доступ (сейчас бессрочно).
