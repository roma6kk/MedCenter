Машина перезагружалась несколько раз; после перезагрузки контейнеры поднимаются сами, а dev-сервер Next — нет.

```bash
docker compose up -d redis traefik postgres hapi rabbitmq analytics-service auth-service catalog-service notification-service appointment-service encounter-service patient-service practitioner-service
```

```bash

```

```bash
npm run seed:demo
```

```bash
cd frontend && node node_modules/next/dist/bin/next dev --port 3000 --hostname 127.0.0.1
```

- `seed:demo` идемпотентен и дополняет свободные слоты на 14 дней вперёд от сегодняшней даты — запускайте, если слоты кончились.

- `npx next dev -p …` ломается из-за хука rtk, поэтому команда запускает `node node_modules/next/dist/bin/next` напрямую.
- После правки сервиса бэкенда: `docker compose up -d --build <service>` и `npm run stack:wait`.

## 4. Чек-лист по ролям

Формат: шаги → ожидаемый результат. FR — из спецификации, сценарии A–F — `specs/frontend-design-spec.md` §6.

### 4.1 Гость и пациент (FR-001…FR-008)

1. **Каталог.** `/`, `/doctors`: список врачей со специальностью, пагинация, фильтр. `/doctors/{id}`: карточка и свободные слоты. `/doctors/does-not-exist` → страница «Врач не найден», HTTP 404.
2. **Сценарий A.** Гость выбирает слот на странице врача → «Записаться» → вход → возврат на шаг подтверждения с восстановленным черновиком → «Подтвердить» → 201, переход на страницу записи.
3. **Сценарий A2.** Два пациента в двух окнах выбирают один слот; второй получает тост «Слот уже занят», слоты обновляются, мастер остаётся на шаге выбора.
4. **Регистрация.** `/register`: ошибки под полями; занятый email → подсказка у поля email; слабый пароль отклоняется так же, как сервером; после выхода черновик записи очищается.
5. **Мои записи.** `/appointments`: вкладки «Предстоящие / Все записи», пагинация. Деталь записи, отмена с причиной 3–500 символов; повторная отмена → понятное сообщение (409 `APPOINTMENT_NOT_CANCELLABLE`). Чужой id записи → «не найдено».
6. **Сценарий B.** Отмена → запись отменена, слот снова свободен у врача и в мастере, появляется уведомление.
7. **История и назначения.** `/history`, `/prescriptions` (нужен пациент с завершённым приёмом — Кузнецов): лекарство с кодом АТХ и дозировкой, направление-услуга без чипа АТХ.
8. **Сценарий E.** `/notifications`: список, фильтр непрочитанных, «прочитано»; счётчик колокольчика обновляется (опрос раз в 30 с).
9. **Профиль.** `/profile`: данные из `/me` и FHIR-карточки `/me/patient`.

### 4.2 Врач (FR-009…FR-014)

1. **Журнал.** `/doctor/appointments`: день, навигация по дням (день в URL `?date=`), статусы, фильтр.
2. **Сценарий C.** На свежей `booked`-записи «Открыть приём» → `/encounters/{id}` (id приёма, не записи). Заполнить: диагноз J06.9 через поиск МКБ-10, измерение 36.6 с единицей `Cel` (единица теперь не подставляется сама — её нужно выбрать), назначение J01FA10 → «Завершить приём» → режим только для чтения с баннером. Enter в однострочном поле приём не завершает; двойной клик отправляет один запрос.
3. **Сценарий C2.** Повторная отправка из второй вкладки → 409 → форма только для чтения с сохранёнными данными; перезагрузка страницы → по-прежнему только чтение.
4. **Статус записи после приёма (новое в бэкенде).** После завершения запись становится `fulfilled` («Состоялся»). Проверить, что в журнале у такой записи нет действий «Открыть приём» / «Неявка» — клиент ещё не адаптирован к этому (см. §6).
5. **Неявка.** На свежей `booked`-записи без приёма «Неявка» → `noshow`. На записи с открытым или завершённым приёмом сервер теперь отвечает 409 `ENCOUNTER_STATE_INVALID` — проверить, как это показывает интерфейс.
6. **Ошибки кодов.** Неизвестный код МКБ-10 (например `Z99.99`) или АТХ (`Z99ZZ99`) → ошибка у соответствующего поля, фокус на нём.
7. **Расписание и карточка пациента.** `/doctor/schedule`; `/patients/{id}`: шапка, связанные лица (в демо их нет — пустое состояние), история, назначения.

### 4.3 Администратор (FR-015…FR-021)

Агент интеграции админку в браузере не проходил — проверить внимательнее.

1. **Пользователи.** Список, фильтр по роли, создание пациента/врача/админа, редактирование, деактивация; занятый email → ошибка у поля; врач привязывается к PractitionerRole (пока поле ввода id, не список — §6).
2. **Услуги и кабинеты.** Списки, создание, правка, удаление; удаление используемых → `SERVICE_IN_USE` / `ROOM_IN_USE`; «Использование» кабинета. **Новое:** кабинет с уже занятым номером (в том числе в другом регистре) → 409 `CONFLICT`.
3. **Сценарий D.** Расписания: создать расписание (врач, кабинет, услуга, горизонт, окна по дням, длительность слота) → сгенерировать слоты за период → слоты видны в сетке, у врача в расписании и у пациента в мастере. Пересекающееся расписание → `SCHEDULE_OVERLAP` с подсветкой окон; удаление с занятыми слотами → `SCHEDULE_IN_USE`.
4. **Терминология.** Список value set'ов; импорт снапшота `1.4.463` → 202; неизвестная версия → понятная ошибка.
5. **Сценарий F.** Аналитика 9.1–9.3 с периодом; журнал аудита с фильтрами по периоду, типу ресурса и пользователю, копирование `requestId` (только у событий, где он не пустой).
6. Тестовые сущности называйте с префиксом `E2E-check` и удаляйте после проверки; демо-данные (кабинеты 101/112…, 6 услуг и расписаний, демо-пользователи) не трогайте.

### 4.4 Сквозное

- Язык RU/EN (переключатель в шапке, в том числе на `/login` и `/register`): все тексты, заголовки вкладок, сообщения валидации.
- Клавиатура: один skip-link «Перейти к содержимому», видимый фокус, диалоги держат фокус, Escape закрывает.
- Ширина 375 px: нет горизонтального скролла, меню переносится, цели не меньше 44 px.
- Сеть: DevTools → Offline на любой странице со списком → баннер «Нет связи с сервером», «Повторить» не теряет фокус.
- Безопасность: пациент на `/admin/*` и `/doctor/*` → 403/перенаправление; в `localStorage`/`sessionStorage` нет токенов (черновик записи — да, токены — нет); `http://localhost:8081/fhir/Patient` → 404, `/fhir/metadata` → 200.

## 6. Известные недочёты (ожидаемы при тестировании)

Клиент ещё не адаптирован к новому API (§5):
- вкладка «Предстоящие» показывает и отменённые записи (сервер теперь умеет `status=booked`, клиент не просит);
- каталог фильтрует по специальности в памяти, загружая до 100 врачей (сервер теперь отдаёт `specialtyCode`);
- в форме врача-пользователя PractitionerRole вводится как id, а не выбирается из списка (сервер теперь отдаёт `practitionerRoleIds`);
- у `fulfilled`-записей в журнале врача могут оставаться действия «Открыть приём» / «Неявка»; ответ 409 на неявку может отображаться общим баннером.

Остальное:
- текст уведомлений содержит время в UTC, клиент переписывает его на время Минска регуляркой (лучше структурное поле от сервиса);
- `AppointmentViewDto.createdAt` — только дата, спека говорит RFC 3339;
- изменения кабинетов, услуг и расписаний не пишут `AuditEvent` (по архитектуре аудит обязателен только для encounter, appointment и auth);
- две одновременные записи кабинета с одним номером не ловятся (проверка в сервисе, у HAPI нет уникального ограничения);
- у страницы врача нет скелетона при переходе (компромисс ради настоящего 404);
- уже показанные серверные сообщения у полей не перерисовываются при смене языка до следующей отправки;
- в админке графиков нет (recharts не установлен), сортировка колонок и фильтры в URL не сделаны;
- нет transactional outbox: событие теряется, если брокер упал после записи; два параллельных `POST /encounters` пишут два `AuditEvent`; у HAPI нет healthcheck;
- `requestId` пуст у старых событий аудита.

## 7. Окружение и `.env`

- Локальный git-ignored `docker-compose.override.yml` подменяет `OAUTH_CLIENTS_JSON`: в `.env` клиенту `medcenter-web` не хватает скоупов `user/*.read` и `user/*.write`. Нужно поправить `.env` (и убрать `JWT_ISSUER=https://api.medcenter.by`), после чего override удаляется.
- `.env.example` агентам недоступен — новые переменные (`REDIS_PASSWORD`, `RABBITMQ_PASSWORD`, `BOOTSTRAP_ADMIN_*`, `OAUTH_CLIENTS_JSON`, `APP_PUBLIC_URL`) нужно внести вручную.
- В корне лежит мусорный пустой файл `**For`; `frontend/pw-tmp.config.ts` — локальный конфиг Playwright для установленного Chrome, не коммитить.

## 8. Как вести исправления

- Дефект фиксируйте с ролью, адресом страницы, шагами и ожидаемым результатом; для ошибок API — `errorCode` и `requestId` из баннера.
- По каждому дефекту: `/debugger` (поиск причины) → исправление с тестом → проверка в браузере → коммит `fix(<scope>): …`.
- Проверки перед коммитом: `cd frontend && npx tsc --noEmit && npx jest && npx next lint`; для сервиса `npx nx run-many -t test lint build -p <project> --parallel=1` и `npm run smoke:stack`.
